# Implement

Build the work described by a meldom parent ticket (a spec) or a set of tickets, in this session. This is the single-session, in-context build, and the default build step for every ticket-producing chain. To land a whole spec as one PR with parallel subagents instead, recommend `meldom:implement-spec` and hand back — it is user-invoked only, so you cannot reach it with the Skill tool.

The **scope** is the set of tickets handed to you at step 1 — a parent means all its open children as of that read, unless the user explicitly narrows it — plus **every ticket this session creates**, whatever its type, cause or age. A bug you found beside the seam, a gap the spec skipped, a pre-existing fault in a test or a script: if it is worth a ticket, it is in the scope and you build it here. There is no category of ticket you file and leave. Completion means every ticket in the scope reads `done` or `closed`, each implemented, verified and reviewed in this session. The final message says exactly that, per ticket. It never lists an open ticket, a next step, or anything left for the user — there is nothing left, or you are not finished.

1. **Read the work.** Pull the ticket(s) with `mcp__meldom__ticket_view({ "id": <id> })` — read the parent's body (the spec) and each child's acceptance criteria. Read any `attachments[]` (a mockup/spec image) to ground the build. Read the attached `notes[]` and the project's domain glossary (`CONTEXT.md`, if it exists) so names match the domain language.

2. **Claim the work.** Move the ticket you are about to build — and its parent spec — to `in_progress` with `mcp__meldom__ticket_batch_update({ "entries": { "<ulid>": { "status": "in_progress" }, ... } })`. Key its `entries` by the ticket's **ULID**, the `id` field step 1 returned, never the `KEY-42` form that `ticket_list` prints: `ticket_view` accepts either, but `ticket_batch_update` and `ticket_outcome` take only the ULID and reject a key outright. The board shows what is being worked on right now, so make the move before writing code, not after.

   Then, on the first pass only, report the plan: exactly one step per ticket in the scope in build order and nothing else, each sized `S`, `M` or `L`: `mcp__meldom__progress({ "goal": "<spec title>", "plan": ["<ticket title>:M", "<ticket title>:S"] })`. The plan is the tickets: review, the gate and the rest of the run get no step of their own. A later pass — step 5 or step 6 sending you back to step 1 — never sends a `plan`, because a second one replaces the first. Its tickets reach the plan with `{ "add": ["<ticket title>:S"] }` instead: a follow-up is already there from when you filed it (step 3), and a ticket review sent back to `open` gets a new step, since its first one already reads done. If `mcp__meldom__progress` is not loaded, search your tools for it once; when that finds nothing, skip every progress call in this skill silently and carry on — the ticket moves already tell the board where you are, so there is nothing to retry and nothing to tell the user.

3. **Implement at the pre-agreed seams.** Handing you the work confirms its seams. Call the Skill tool with `meldom:tdd` where a seam is testable — write the failing test at that seam, then the minimal code to pass. Reach for the Skill tool with `meldom:codebase-design` when an interface needs designing.

   Work an in-scope acceptance criterion cannot pass without is in scope: build it. Everything else the build surfaces is a **follow-up**: file it the moment you see it with `mcp__meldom__ticket_create({ "title": "...", "body": "<what you saw, where, and its acceptance criteria>", "parent_id": "<parent ulid>" })`, add it to the progress plan with `{ "add": ["<title>:S"] }` in the same message, return to the criterion you were on, and build it in the next pass (step 5). A follow-up lives inside the family of the ticket you are building, so `parent_id` is always passed: the spec from step 1, or the ticket's own parent. When the ticket you are building is a root with no parent, give it one first — `ticket_create({ "title": "<the ticket's title>", "body": "<one line naming the ticket it groups>", "type": "spec", "parent_id": null })`, then `ticket_update({ "id": "<ticket ulid>", "parent_id": "<new spec ulid>" })` — and file under that spec. A ticket this session filed as a board root is a mistake; reparent it at once.

4. **Verify at the seam.** While you build, run the tests that cover what you just touched, through the project's own test command. Everything that sweeps the whole project waits for the **gate** (step 7).

   Keep the board honest as you go: the moment a child ticket's acceptance criteria pass, `ticket_update` it to `done` with a `reason`, and claim the next one as `in_progress` before starting it. Send its progress `{ "done": <its step number> }` in that same message, never on its own. At any point exactly one ticket is `in_progress` and every finished one reads `done` — never batch the status moves up to the end of the session.

5. **Build what you filed.** An open ticket in the scope is not a stopping point, and "pre-existing", "out of this spec" or "waiting on your call" are not reasons to stop. Call `mcp__meldom__conversation_status` and read the tickets it tracks: if any one this session created is still open, go back to step 1 with those tickets and build them. Repeat until a pass creates nothing new and every tracked ticket reads `done` or `closed`. The one exception is a step only a human can take — a credential, a third-party dashboard, an external system: hand it over through `meldom:wizard` or a question to the user, and leave only that ticket open.

6. **Review, then record the outcome.** Call the Skill tool with `meldom:code-review`, passing `HEAD` as the fixed point. The work is uncommitted, so that reviews exactly what this session built. Its Spec axis is what checks each ticket against its acceptance criteria, so read that report per ticket and set `mcp__meldom__ticket_outcome({ "id": <ulid>, "outcome": "verified" })` for the ones it confirms. A ticket the report contradicts gets `"outcome": "failed"` and goes back to `open` — do not leave it reading `done`. Build it again from step 1, with anything the review made you file.

7. **Run the gate.** Once nothing in the scope is open but a human-only step from step 5, run every whole-project check the repo defines — the full suite, lint, format, typecheck, build — each as its own command, read by its own exit code. Fix what fails and re-run that check. The gate is done when every check exits clean.

8. **Record in meldom, don't commit.** Parent status never rolls up from children, so when every child of the parent is `done` or `closed`, close it explicitly with `ticket_update` to `done` and `reason: "All children done: <summary>"`. Then walk upward — a parent you just closed may complete *its* parent (a `wayfinder:map` over a spec, say) — and repeat until no parent qualifies. Send progress `{ "finish": true }` in the same message as the last tool call of the run. The conversation is already open — it auto-tracks the tickets you touch, so there's nothing to start or finish. Do NOT auto-commit — leave committing to the user or `meldom:ship` (meldom works on `main`; commit at the end, not mid-build).
